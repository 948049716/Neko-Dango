# 《猫咪团子》架构设计

> 版本：1.0 · 日期：2026-10-20 · 状态：待实现的工程蓝图  
> 技术基线：[技术选型](技术选型.md) · 规则基线：[主策划 v2.2.0](../猫咪团子_全案策划与技术设计规范.md)

## 1. 架构目标与边界

采用模块化客户端加轻量云后端。客户端独立运行本局物理和规则，云端管理永久资产与账号数据。3D 表现、物理状态、玩法规则和微信能力分别拥有明确边界，便于换资源、调手感、测试与后续平台迁移。

首期包含投放、11 级合成、危险线、道具和基本结算；不建设实时多人服务器。首发完整版本逐步接入广告、收藏、装扮、离线收益和每日挑战。

## 2. 分层与依赖关系

| 层 | 模块 | 责任 | 允许依赖 |
| --- | --- | --- | --- |
| 交互表现 | HUD、CatView、CameraController、VFX、AudioManager | 输入转命令，依据只读快照/事件播放表现 | 应用层接口、Cocos、平台抽象 |
| 应用编排 | GameSession、FlowController、PropCoordinator、MergeCoordinator | 每步流程、事务、暂停与恢复 | 规则层、端口接口 |
| 规则领域 | CatState、SpawnPolicy、DangerRules、ScoreRules、EconomyRules | 纯数据与规则计算 | 基础类型、固定配置、显式随机源 |
| 基础设施 | PhysicsAdapter、AssetService、SaveRepository、Telemetry | 物理后端、资源生命周期、持久化、诊断 | Cocos 或具体 SDK |
| 平台接入 | WeChatAdapter、WebAdapter，后续 DouyinAdapter | 广告、生命周期、分享、存储、安全区 | 平台 SDK |
| 云端 | 账号、配置、账本、收益、关卡、排行榜服务 | 权威永久状态、鉴权、事务与审计 | CloudBase SDK |

依赖由启动入口装配。规则层禁止导入引擎节点、`wx`、网络 SDK 和真实时钟；物理接触输入用普通数据表示。可靠业务流程采用显式方法调用，已经提交的结果再通过有类型事件通知 UI，避免依赖事件订阅先后顺序发奖。

## 3. 建议目录

以下为待建结构，当前目录尚无这些引擎代码。

```text
client/                         Cocos 项目根
  assets/
    scripts/
      bootstrap/                依赖装配、启动和场景切换
      domain/                   纯 TypeScript 规则和数据

      infrastructure/physics/   Bullet 接入、单位换算
      infrastructure/storage/   本地快照、迁移、云端仓库
      infrastructure/assets/    Bundle 加载、引用和缓存
      platform/                 接口、微信/H5 适配
      presentation/             UI、角色、镜头、音频
    bundles/                    按技术选型的资源组组织
    configs/                    本地默认配置
  settings/                     引擎项目配置
server/
  functions/                    云函数入口
  domain/                       权威经济规则
  repositories/                 数据访问和事务
shared/                         请求协议、配置类型、纯校验逻辑
tools/                          资产审计、配置校验、构建辅助
```

`shared` 通过构建期复制或受支持的本地包引入，不能假设 Cocos 会自动编译项目外目录。引擎 `.meta` 与资源一起提交。现有高模目录保留为源资产，禁止自动复制进游戏资源目录。

## 4. 关键数据与版本

| 数据 | 关键字段 | 不变量 |
| --- | --- | --- |
| RunContext | runId、sessionEpoch、tick、seed、rngState、rulesVersion、physicsVersion、configHash | 一局规则版本固定；重开递增 epoch |
| CatEntity | entityId、generation、level、state、position、velocity、firstContactTick | ID 与 generation 共同标识一次对象池租用 |
| MergeTxn | txnId、entityRefs、reservedTick、commitTick、status | 实体只能被一个未完成事务占用 |
| PropTxn | txnId、type、targetRefs、reservationId、status | 成功消耗一次；失败释放预占 |
| ContactPair | 有序实体对、firstContactTick、lastContactTick、normalSpeed | 接触中断即重置连续计时 |
| SaveEnvelope | schemaVersion、revision、payload、checksum、savedAt | 校验码只防损坏，不提供防作弊 |
| WalletLedger | uid、requestId、reason、delta、balanceAfter、serverTime | 同账号同请求只入账一次 |

命令包括 Drop、EnterProp、ConfirmProp、CancelProp、Pause、Resume、RequestRevive。命令携带 runId、epoch、序号与目标 tick；平台异步回调还要关联业务事务，旧局回调不得改变新局。

配置集中定义半径、质量、阻尼、合成速度阈值、接触时长、掉落池、危险线和道具白名单。构建期检查等级完整、概率和正确、数值范围以及资源 ID 存在。远程配置通过版本与结构验证后缓存，下局才生效。

## 5. 物理坐标与主循环

玩法数据统一以 lu 表示，适配层建议以 `100lu = 1 个引擎世界单位` 转换，防止直接把数百 lu 当成物理米使用。容器宽 6.4、危险线高 6.6，Lv11 半径 1.8；长度、速度、加速度分别一致换算，角度与质量采用明确约定。重力、摩擦和阻尼需灰盒调优后入配置。

刚体根节点保持单位缩放，SphereCollider 半径通过尺寸字段设置。视觉根跟随刚体位姿，但果冻、表情和挂点缩放都在独立子节点内。静态墙使用厚壁盒代理，视觉藤编不参与碰撞。

每个逻辑 tick 按固定顺序执行：

1. 拒绝旧局、重复和当前状态不允许的命令，消费合法输入。
2. 提交到期的合成/道具事务，更新物理对象；不在碰撞回调中增删刚体。
3. 以 1/60s 推进物理，收集接触快照；按需要使用 2～4 子步，总时长仍为 1/60s。
4. 更新首次接触标记，构建有序候选对；连续接触与法向相对速度均符合时预占合成事务。
5. 对排除合成/回收实体后的局面更新高度、危险计时、Combo 和掉落阶段。
6. 输出只读状态与领域事件，更新诊断缓冲；渲染读取快照并插值。

候选按实体 ID 稳定排序，不能依赖后端碰撞回调顺序。接触中断清零累计时间，休眠接触通过适配层的持久接触集合或经验证的接触查询维护，不能只依赖一次 enter 回调。

卡顿时限定每渲染帧的追赶次数，例如初值 4 次；不把大 dt 塞进求解器，也不偷偷跳过逻辑 tick。持续积压则降级或进入受控暂停并记录异常。后台期间暂停游戏时钟，返回不补跑离线时长。

## 6. 状态机与互斥

使用“全局流程 + 单局阶段 + 道具阶段 + 实体状态”分层，避免把所有组合塞进一个巨大枚举。

| 状态维度 | 状态/规则 |
| --- | --- |
| 全局流程 | Boot、Loading、Home、InRun、Result；Paused 作为覆盖态保存返回上下文 |
| 单局阶段 | Playing、Danger、Frozen、Reviving、Settled |
| 道具阶段 | Idle → Targeting → Confirmed → Resolving → Cooldown |
| 猫咪状态 | 依据主策划生命周期实现；Preview/Falling/Merge/Despawn 排除危险判定，首次有效碰撞后转入可结算状态 |

Danger 禁止新的投放释放，允许瞄准；只开放香酥鱼干与逗猫棒。Targeting 暂停投放但继续物理；Resolving 锁其他道具，倒计时继续。镜头在 Targeting、结算、广告恢复和危险最后 1 秒锁定。

暂停采用原因集合，例如 user、background、ad、audioInterruption。每个来源只移除自己的暂停原因；集合清空且前台状态允许时才恢复，避免广告关闭时提前恢复仍在后台的局面。音频独立保存用户静音偏好及中断前播放状态。

## 7. 合成事务与失败边界

合成条件来自主策划：同等级、法向相对速度低于 80lu/s、连续接触至少 50ms。阈值配置化，固定 60Hz 下 50ms 对应 3 个完整 tick。

预占阶段同步检查并锁定两个实体的 ID/generation，将它们移出后续候选及危险集合；在安全阶段移除物理体，保留视觉代理播放演出。普通合成在 27 个逻辑 tick 后提交，双 Lv11 在 36 tick 后提交。逻辑计时决定完成，动画结束回调仅清理表现。

普通合成按质心生成新等级实体、继承受限速度、施加受限冲击波并结算一次分数；双 Lv11 只移除并加 4096 分，绝不创建 Lv12。事务成功后再回收旧对象。局面冻结、重开或 epoch 改变会取消未完成事务，并丢弃其后计分事件。

可有多组互不相交的实体事务；“合成生成锁”用未完成事务计数表达投放限制，不能用单个动画的结束覆盖其他事务。危险线每 tick 采样剩余有效对象，锁结束再立即采样，不能用连锁合成暂停失败计时。

投放节奏同时满足：上一只释放后至少 0.35s 才展示下一只；再次释放还需上一只首次有效碰撞或已过 0.90s，并且无生成锁、非危险态、非道具互斥态。

危险判定使用 `positionY + radius`，不读视觉包围盒。单体连续越线 0.60s 进入 3 秒倒计时；全部安全持续 0.30s 才解除。失败 tick 进入 Frozen 后不再接受物理、合成和计分。复活按顶边高度降序、ID 升序移除最高两个合法对象，清零速度，等待 0.30s 后恢复，一局最多一次。

## 8. 道具与表现调度

道具开始时预占库存，确认目标时检查状态与 generation。有效执行才提交消耗；目标已合成、取消选择、彩虹球触及 Lv11 等不合法情况释放预占。力场只作用于活跃合法刚体，忽略 Merge/Despawn 对象。云端永久库存由流水入账，局内预占额度不能被多次并发消费。

CharacterPresenter 接收碰撞冲量、状态与演出事件；SquashController 计算压缩和体积补偿；FaceController 管理微表情；PerformanceDirector 统一派发主动作和邻猫互动；AudioManager 按合成、危险、道具、闲置的优先级分配声道。

稳定 1.5s 且速度小于 5lu/s 时进入低频表现更新。物理休眠与表现休眠分别管理，表演可以临时唤醒脸和四肢，不应给物理刚体额外施力。共享材质保留复用；必须独立的形变参数需要实测材质实例/合批成本。

## 9. 镜头、输入与适配

布局沿用 750×1334 设计画布及安全区等比缩放。物理容器宽始终为 640lu，折叠屏只扩展背景。默认透视 FOV 初值 30°，水平观察范围 ±16°；镜头不改变世界重力或玩法平面。

输入按 UI → 道具 → 投放区域 → 镜头背景区域的优先级分发。同一触点从按下到抬起只归一个控制器，防止瞄准过程中突然变为转镜头。屏幕射线与 Z=0 求交，投放 X 限制在墙边减去当前半径的合法范围。

回放保存转换后的世界空间输入，不保存像素坐标。因此镜头角度测试应使用同一组世界坐标命令；同一屏幕像素在不同镜头下不应被当作相同物理输入。

## 10. 平台接口与广告事务

| 端口 | 返回语义 |
| --- | --- |
| showRewardedAd(placement, attemptId) | completed、cancelled、noFill、failed、unsupported |
| showInterstitial(placement) | shown、skipped、failed、unsupported |
| shareSnapshot / saveSnapshot | success、cancelled、failed、unsupported；不触发奖励 |
| storage | 版本化读写、失败结果与容量异常 |
| lifecycle / audioLifecycle | 前后台和音频中断事件 |
| safeArea / capabilities | 当前安全区、能力支持状态 |

具体 `wx.*` 只在 WeChatAdapter 内使用。广告完整观看判断和事件字段需按选定基础库验证；无法确认完成时不得发放观看奖励。无广告时可显示普通返回入口，主策划的每日爱心补给独立做限额事务，不能复用“观看成功”。

流程：用户点击 → 服务端创建限时 rewardAttempt → 播放广告 → 平台回调归一化 → 服务端按 attemptId/账号/业务场景校验 → 事务提交奖励及流水 → 客户端应用服务端结果。超时后查询原 attempt，不创建新奖励；奖励成功但响应丢失时重试返回同一结果。

客户端 completed 结果本身不是可信防作弊凭证。若广告渠道提供可验证的服务端完成证据，接入并核验；若不提供，必须记录残余风险，采用频控、单局/每日额度与异常审计，不能宣称服务端已证明观看真实。

## 11. 云端服务与数据库

| 服务/操作 | 输入 | 服务端责任 |
| --- | --- | --- |
| bootstrap | 客户端版本、配置版本 | 从可信上下文识别账号，返回服务器时间/配置/存档版本 |
| startRun | 模式、规则版本 | 签发 runId，冻结种子/配置/允许奖励额度 |
| settleRun | runId、requestId、结果摘要、必要事件 | 检查会话、规则范围、次数和异常，结算一次 |
| claimOfflineIncome | requestId | 用服务端 lastClaimAt 和当前时间计算，最多 8 小时 |
| purchaseDecoration | requestId、商品 ID、预期 revision | 事务内检查价格、余额、已有权益并扣款发放 |
| beginReward / claimReward | 场景、attemptId | 限额、状态迁移与幂等奖励 |
| getDailyPuzzle | 客户端版本 | 按服务端业务时区返回固定题目与版本 |

业务日期建议统一 Asia/Shanghai，与玩家设备时钟无关。账号从认证上下文读取，不相信请求中自报的 uid/openid。

数据库至少包括 profiles、wallets、inventory、ledger、runs、rewardAttempts、configs、dailyPuzzles、leaderboardEntries。账本主键使用账号与 requestId 的确定性组合；在同一数据库事务中校验余额/版本、更新状态、写入流水。若存储实现不能保证这些操作原子完成，就不应发布消费接口。

文档型数据需控制单文档大小；回放大对象存云存储，仅在数据库保存索引。排行榜按模式、关卡/规则版本分榜，索引围绕榜单 ID 与得分建立。客户端上报分数只可作为候选；MVP 校验只能发现部分异常，不能证明物理过程真实，高价值奖励榜在权威校验建立前不开放。

## 12. 存档、离线与恢复

本地分为设置、单局快照、永久资产缓存和待提交请求。服务器余额覆盖本地缓存，不用两个快照的余额相加解决冲突。首次联网建立账号后，再关联游客待校验记录，防止跨设备重复结算。

本地快照采用双槽：写入新槽 → 校验 → 切换当前 revision；旧槽保留作恢复。只保存无未决合成/道具事务的稳定快照；中途切后台优先保存最近稳定点与其后的输入日志，不序列化正在运行的动画 Promise。恢复可能回到最近稳定点，需明确显示恢复状态。

引擎内部接触缓存不完整序列化，刚体位置速度快照恢复不承诺逐位一致。竞技局恢复需标记，不能直接用于严格榜单证明。版本不兼容时保留永久资产和原始备份，放弃不兼容单局并说明；不使用默认存档覆盖云端资产。

弱网重试使用稳定 requestId 与退避策略。离线挑战不进入正式排行榜；永久奖励待联网核验，失败结果必须可查询，不让玩家反复看广告来弥补响应丢失。

## 13. 资源、配置与发布

AssetService 负责引用计数与加载并发，页面只申请/归还资源句柄。角色对象池预热常用等级，记录 active、pooled、leased 数，回收必须清除事件、计时器、材质临时状态和旧 generation 引用。

远程 manifest 包含资源版本、哈希、大小与兼容客户端范围。资源以版本路径发布，完成后再切换 manifest；失败使用本地默认配置或缓存的上一兼容版本。代码升级走平台发布流程，配置回滚不得跨越客户端支持范围。

流水线依次检查：配置合法性、纯规则测试、引擎导入与构建、包体及资源清单、开发工具冒烟、真机矩阵、发布资料。发布记录至少保存 clientVersion、编辑器补丁号、physicsVersion、configHash、assetManifestVersion、基础库测试范围。

## 14. 诊断、测试与验收

埋点沿用主策划的 run、drop、merge、danger、prop、ad、reward 事件。附带运行版本、设备档位、tick、runId 和事务 ID；不采集与玩法无关的信息。高频日志保存在固定容量环形缓冲，仅异常时按限额上传。

| 场景 | 验收不变量 |
| --- | --- |
| 三只同级同 tick 接触 | 任一实体最多被消费一次，结果顺序稳定 |
| 合成途中重开/失败 | 旧动画和延迟回调不生成新猫、不加分 |
| 高速擦碰/接触中断 | 未满 50ms 或速度超限不合成 |
| 对象池复用 | 旧 generation 不能作用于新实例 |
| 危险线抖动 | 0.60s 进入、0.30s 全部安全解除；视觉变形不影响高度 |
| 广告重复关闭/网络重试 | 一次 attempt 最多发奖一次 |
| 广告+切后台交叠 | 所有暂停原因解除才恢复 |
| 云端结算响应丢失 | 原 requestId 查询/重试，不重复加钱 |
| 升级存档损坏 | 退回有效槽位，保留云端永久资产 |
| 镜头 ±16° | 同世界坐标输入得到相同规则输入；触控区域不串扰 |
| 20 猫持续 10 分钟 | 无明显穿模、无持续内存增长、池与监听器数量稳定 |

纯规则测试与真实引擎物理测试分开：1000 局无头规则测试不能代替真机堆叠验证。性能按设备/画质/目标帧率分别统计 CPU、GPU、帧时间、内存和加载时间；30fps 档按对应帧预算验收。

## 15. 实施顺序及需澄清的规格

先建立引擎工程、单位转换和灰盒主循环，再实现事务、危险线与回放日志；用 3 只低模完成视觉切片后才批量生产 11 级角色。随后接四道具与平台生命周期，最后接永久经济、广告和外围玩法。

与主策划相比，本文明确提出四项需同步修订的技术口径：GLB 是导入交换格式；跨设备浮点回放不承诺严格一致；30fps 档使用独立验收预算；每日一题且 30 天不重复需要至少 30 个不同题目。原策划文件本次未改动，冻结版本时应统一更新，避免研发同时遵循矛盾要求。

最终选型以 [技术选型中的验证门槛](技术选型.md#7-工程与验证门槛) 为准；当前没有任何真机性能、广告接入或云端部署完成的结论。
