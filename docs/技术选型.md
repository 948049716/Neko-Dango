# 《猫咪团子》技术选型

> 版本：1.0 · 日期：2026-10-20 · 状态：推荐决策，待 M0/M1 真机验证后冻结  
> 适用：微信小游戏首发，后续预留抖音与 H5。  
> 配套：[架构设计](架构设计.md) · [主策划 v2.2.0](../猫咪团子_全案策划与技术设计规范.md) · [3D 美术规范](../art/美术设计与资源清单_3D.md)

## 1. 选型结论

推荐 **Cocos Creator 3.8 LTS 系列 + TypeScript + Bullet 3D 物理 + 微信原生能力适配 + CloudBase 轻后端**。采用 3D 模型呈现、XY 平面受约束堆叠、纯视觉果冻形变。首期先做可离线运行的核心切片，外围经济和排行榜再接云端。

本文基于“小型团队、尚无既有引擎代码、微信首发”的假设。3.8 是推荐版本线，不代表已安装或已锁定版本；具体补丁号、物理运行模式及最低微信基础库版本，必须在首个真机切片通过后写入版本清单。

| 层面 | 推荐方案 | 本项目理由 | 验证与边界 |
| --- | --- | --- | --- |
| 游戏引擎 | Cocos Creator 3.8 LTS 系列 | 统一处理 3D 场景、UI、资源与小游戏构建 | 固定编辑器补丁号与构建参数 |
| 业务开发 | TypeScript，规则模块启用严格类型检查 | 配置、状态机、事务边界便于维护 | 规则层不依赖 `cc` 和 `wx` |
| 物理 | 引擎集成 Bullet，单球碰撞体 | 满足球体堆叠、轴向约束及固定步长需求 | 真机验证 WASM/兼容模式、CCD 和接触事件 |
| 视觉 | 简化光照材质、少量骨骼、程序化 Squash & Stretch | 角色有体积，成本集中在轮廓和五官 | 不做真实软体、实时毛发和复杂折射 |
| 界面 | 引擎内置 UI、图集、预制体 | HUD 与 3D 生命周期统一 | 不引入 React/Vue 到游戏运行时 |
| 资源 | Blender 制作低模；GLB/FBX 作为导入源；引擎资源用于交付 | 复用现有 GLB，转换为适合运行时的产物 | 不直接发布当前高模文件 |
| 资源加载 | Asset Bundle、小游戏分包、远程静态资源 | 将首屏、角色和主题拆开加载 | 本地分包与远程包是不同发布方式 |
| 配置 | JSON + 构建期结构/数值校验 | 半径、概率、道具和经济可版本化 | 单局固定配置，不在局中替换规则 |
| 后端 | CloudBase 云函数、文档数据库、云存储 | 覆盖账号、存档、经济流水和配置，减少运维 | 云端不承担每帧物理计算 |
| 测试与协作 | Git + LFS；TypeScript 规则测试；真机集成测试 | 代码与大体积美术分开管理，保护规则边界 | 测试工具只用于开发，不打入小游戏 |

Cocos 官方提供微信小游戏构建流程，输出对应平台工程配置；这是选择它作为首发引擎的直接依据。[微信小游戏发布文档](https://docs.cocos.com/creator/3.8/manual/en/editor/publish/publish-wechatgame.html)

## 3. 引擎方案比较

以下是针对本项目开发成本的判断，不是通用性能排名；未对备选引擎做相同设备基准测试。

| 方案 | 适用条件 | 本项目判断 |
| --- | --- | --- |
| Cocos Creator + TypeScript | 微信优先，3D 与 UI 混合，小团队 | 推荐：先用完整编辑器工作流打通角色、物理与平台 |
| Three.js + 独立物理库 | 已有成熟 Web 3D 代码和小游戏适配经验 | 备选：需要额外整合 UI、资源、生命周期与平台构建 |
| Unity + 微信转换链路 | 团队已有大量 Unity 代码、美术管线和经验 | 当前没有相关沉淀，增加一条转换与验证链路的收益不足 |
| 2D 引擎/渲染 + 预渲染角色 | 接受固定视角、削减立体观察需求 | 不满足当前 ±16° 观察和完整 3D 角色方向 |

若后续确认团队有成熟 Unity 或 Three.js 项目基础，可重新评估；不因单个模型导入失败就更换整套引擎。

## 4. 物理与视觉决策

### 4.1 Bullet 为主选，Cannon 仅作验证备用

采用引擎集成版本，避免另装一套独立物理库。Cocos 官方列出了 Bullet、Cannon、PhysX 与 builtin 的支持差异，其中 builtin 只有碰撞检测，不适合本项目的动态堆叠。[物理引擎说明](https://docs.cocos.com/creator/3.8/manual/zh/physics/physics-engine.html)

先用 Bullet 完成 20 猫堆叠基准；若运行模块加载或首包成本不能达标，再以相同测试场景评估 Cannon。更换后端需要重新调摩擦、弹性、求解参数并变更物理版本，不允许运行中动态替换。

二维圆碰撞配 3D 外观在几何上可行，但主策划明确要求 3D 球体及约束，因此不作为本轮默认方案。未来若转用二维物理，必须更新技术规范并重新验收手感。

### 4.2 约束与时钟

每只猫一个居中的 SphereCollider，位置限制在 Z=0；平移自由度为 X/Y，旋转自由度仅为 Z。逻辑按 60Hz 固定步运行，渲染可独立降至 30fps。

CCD 是需要验证的能力，不是穿模兜底承诺。官方说明 Bullet CCD 对单形状、碰撞中心等有约束，当前单球结构应按该要求设计。[CCD 支持范围](https://docs.cocos.com/creator/3.8/manual/zh/physics/physics-ccd.html)

果冻形变只缩放视觉子树，体积近似守恒；不能缩放物理根节点。脸部挂点只接受部分形变，四肢和耳尾在绑定后独立驱动。先用节点缩放跑通手感，再按视觉需要增加骨骼/着色器形变。

### 4.3 回放能力边界

固定步长和随机种子不自动保证浮点物理跨设备一致。承诺分三层：

1. 规则层：相同配置、接触事件与输入得到相同计分和掉落结果。
2. 指定构建与运行环境：输入回放通过实测后，才作为该环境的物理回归基线。
3. 跨设备：保存状态快照与关键事件用于诊断/观战，不用客户端回放证明成绩真实。

主策划“同逻辑版本重放必须一致”的要求需要据此补充验收环境。如果必须跨平台严格重模拟，应单独立项确定性物理方案，不能把 Bullet 浮点求解视为已满足。

## 5. 资产管线与加载方案

工作流为：保留原始高模 → 低模重拓扑/减面 → 烘焙贴图 → 拆件与统一绑定 → 制作通用动作 → 导出 GLB/FBX → Cocos 导入 → 建立预制体 → 真机验收。

Cocos 支持 glTF/GLB、FBX 模型导入；实际运行时使用构建后的引擎资源。现有规范中“运行时采用 GLB”在此收敛为“GLB 作为交换与导入格式”，首发不额外开发通用 GLB 在线解析器。[模型资源文档](https://docs.cocos.com/creator/3.8/manual/zh/asset/model/mesh.html)

材质扩展先转为引擎可控的简化材质，检查透明、法线、色彩空间、蒙皮与脸部轮廓。纹理压缩采用选定版本在目标机实测可用的格式；KTX2/Basis 保留为候选，未验证前不作为强制依赖。必须同时记录下载体积和解码后的内存，不能以 GLB 文件大小代替 GPU 内存预算。

| 资源组 | 内容 | 加载时间 |
| --- | --- | --- |
| 启动核心 | 加载页、通用 UI、必要代码、默认配置 | 启动时 |
| 基础玩法 | 猫窝、Lv01～06 LOD1、必要音效、占位体 | 开局前，成功后才允许投放 |
| 高阶角色 A | Lv07～09 | 基础组就绪后后台预取，升阶前检查 |
| 高阶角色 B | Lv10～11 | 基础组就绪后后台预取，升阶前检查 |
| 外围资源 | 图鉴 LOD0、主题、收藏背景 | 进入相关页面前 |

基础包包含各等级可区分的低成本占位表现。高阶资源失败时继续使用正确等级/半径的占位体并重试，避免下载延迟阻断合成。共享材质应由公共资源组持有，切主题不能释放正在被猫咪引用的资源。

Asset Bundle 可映射小游戏本地分包，也可交付远程资源；微信不能把远程脚本加载当作业务代码热更新。代码随审核包发布，远程仅发布合规的资源与配置。[Asset Bundle](https://docs.cocos.com/creator/3.8/manual/zh/asset/bundle.html)、[小游戏分包](https://docs.cocos.com/creator/3.8/manual/zh/editor/publish/subpackage.html)

包体限制、基础库最低版本、广告与权限要求在提审前核对微信官方当期规则，本文不将历史额度写成永久上限。本次微信广告官方页面未成功获取，广告接口行为仍列为平台接入验收项。

## 6. 后端与数据方案

首期以 CloudBase 云函数处理登录态、存档同步、经济交易、离线收益和排行榜候选提交；文档数据库保存业务状态，云存储保存版本资源和受控诊断文件。其官方说明覆盖小游戏与云端数据能力。[CloudBase 应用场景](https://cloud.tencent.com/document/product/876/20232)

客户端负责本局即时反馈，服务器负责永久资产和奖励流水。数据库不开放客户端直接修改余额、道具、排行榜和广告发奖记录。离线局可以游玩，但产生的永久奖励先标记待校验，不用本地时钟计算可直接入账的挂机收益。

不引入多人帧同步、独立 Redis、消息队列或微服务拆分；当前是单机合成玩法，先由模块化云函数承载。未来根据真实并发、慢查询、账务争用和费用数据再扩容。

费用估算采用“日活 × 每人日请求数 × 请求单价 + 数据库读写/存储 + 资源下载流量”，上线前设置预算告警。高频物理事件保留本地环形日志，批量/采样上传，禁止每帧请求云端。

## 7. 工程与验证门槛

固定编辑器、TypeScript、云函数运行时和依赖锁文件；运行时版本选择以部署环境支持矩阵为准。Git 跟踪代码、配置和 `.meta`；大模型/源纹理采用 LFS，构建缓存不入库。开发、测试、生产使用独立云环境，密钥只放部署侧。

| 阶段 | 必须交付 | 通过条件 |
| --- | --- | --- |
| M0 规则与物理灰盒 | 11 级占位球、投放/合成/危险线、回放日志 | 1000 局规则模拟不重复消费、不生成 Lv12；引擎场景另测接触 |
| M1 垂直切片 | 3 只低模、果冻形变、±16°镜头、1 个救场道具 | 20 猫运行 10 分钟；物理及表现解耦；完成微信真机验证 |
| M2 表现生产 | 11 级低模、统一绑定和动画、表演调度 | 极限形变/镜头下无明显脱件，对象池稳定 |
| M3 外围闭环 | 四道具、经济账本、装扮、存档、残局 | 幂等重试、断网恢复与存档迁移通过 |
| M4 平台性能 | 广告、资源加载、降级、发布配置 | 真机矩阵、广告中断、后台恢复和包体检查通过 |
| M5 小规模验证 | 200+ 局有效测试、版本化调参记录 | P0 清零，规则与平台资料复核 |

立项先登记具体低端 Android、主流 Android 和受支持 iPhone 型号。主流目标 P95 帧时间 ≤16.7ms；低端未锁 30fps 档目标 ≤22ms。若使用 30fps 兜底，应另以约 33.3ms 帧预算验收并记录产品降级决策，不能继续宣称满足 22ms。DrawCall 普通 P95≤60、合成峰值≤90 为初始目标，必须以真机数据确认。

现有“21 题且 30 天不重复”的每日残局要求不自洽：若每天一题且连续开放，至少需要 30 个不同题目，或调整重复窗口。严格自动求解器也需要独立工作量，不能视为配置表附带功能。

现有 30～45 人日是原策划估算，未覆盖本次发现的高模重拓扑、完整绑定与动画补齐成本；资源验收前不能沿用为交付承诺。
